# Quickie

Quickie is an iOS launcher built around a single text input: the user types or taps, the app fuzzy-matches against a list of capabilities, and the user decides what to do with the input. "Input text and decide what to do with it after."

## Language

**Action**:
A single invokable capability shown in the fuzzy list (e.g. Open App, Web Search, Copy Snippet, Run Shortcut, Calculate). There is exactly one type of thing in the index — an Action — and every subsystem (fuzzy finder, indexing, favorites, fallbacks) operates on it. An Action has an execution lifecycle (selected → optionally collecting input → presenting results), so a multi-step capability is still a single Action, not a separate concept.
_Avoid_: Command, Workflow (reserved — see below), Item

**Main action**:
The single default behavior an Action (or result row) performs when tapped — open a static [[Custom Action]] in the browser, open a file, run a Shortcut, copy-and-stage a math result. Every row in the result list is presented by its main action. Running a main action **resolves the query**: the input clears back to [[Home]] — except the two staging outcomes ([[Stage]], copy-and-stage), which *replace* the query with the staged text (a fresh, unresolved query), and **opening a file preview**, which leaves the query intact because previewing is part of the searching process, not its resolution (the [[Search Files context]] filter is likewise untouched). A [[Secondary action]] never touches the query.
_Avoid_: Default, primary (use "main action")

**Secondary action**:
A one-shot action reached from the row's long-press menu — the *same* menu that carries Pin/Unpin, not a competing gesture, and the same menu a [[Shelf]] button opens (there, prefixed by the action's title as a non-action row, since an icon-only circle can't name itself). Most secondary actions operate on a specific result's [[Result content]], and their eligibility is a pure function of that Result content, **not** its content type. The content-keyed set is `copy` and `share` on any value-bearing row (text, URL, number, or Pile entry) plus `revealInFiles` on a file and `edit` on every **user-authored, editable** record — a [[Snippet]] and a static [[Custom Action]] each add `edit` (open its in-app editor) *on top of* copy/share, being stored, titled records that still carry a value, unlike a bare text value or a value-only URL; a [[Shortcut Action]] and a [[Custom Action]] each expose `edit` **alone** — a Shortcut deeplinks into the Shortcuts app's editor for the shortcut by name (`shortcuts://open-shortcut`) and a Custom Action opens its live-mirroring editor, since each is an editable *reference* with no pre-resolved text or URL to copy or share (a Custom Action's URL only exists once its slots are filled); a [[Pile]] entry additionally exposes **Remove from Pile** (its home for per-row discard, since the main action stages rather than removes). The one exception to the Result-content rule is **Copy action deeplink**, keyed by the row's **id** rather than its content: it copies the row's `quickie://run/<id>` URL and is offered on **every row whose deeplink runs to an effect** — a content-less command row included, which therefore exposes it *alone* alongside Pin/Unpin (that row has an addressable id even though it has no Result content). The one row it is **withheld** from is **Save for later**: its main action silently writes the typed query into the Pile, so its `quickie://run/<id>` does nothing without a query and copying it is pointless — and since that row also offers no Pin ([[Favorite]]), its long-press menu is empty (issue #140). New Snippet keeps the verb — run standalone it opens the Snippet editor, a real effect. It always sits last in the menu, after any content verbs (ADR 0017; issue #120). Multi-step actions that need a target, date, or name (Make-reminder, Make-Quicklink) are deferred to a later breadcrumb-seeding slice. Distinct from Fallback/content-on-the-text actions, which appear as their own rows rather than behind long-press.
_Avoid_: Context action, more actions

**Result list**:
The single, reversed (bottom-anchored, best match nearest the input/thumb) list shown while typing. Composed of: fuzzy name-matches over Actions, type-triggered results injected with boosted rank by Dynamic Providers (e.g. a math result on top), and Fallback Actions that consume the raw input text as content. All appear as ranked rows; nothing essential is hidden behind a gesture. Its rows are **content, not chrome**: things to read and pick from, so they do not wear the Liquid Glass the input bar, the [[Shelf]] and the [[Favorites grid]] float in (ADR 0042) — the same holds for [[Home]]'s Recent rows, the [[Search Files context]]'s rows and a capture's choice rows, which are the same list in other clothes.
_Avoid_: Results, suggestions, search results

**Settings**:
The app's top-level preferences page and the **per-action hub**, reached like any capability — by typing to surface a "Settings" command row, not via chrome (the old top-right gear button is gone). It has two sections: an **app-level** section (**Appearance** — Light / Dark / System, defaulting to System, applied app-wide; a **Clipboard prefill** on/off toggle; a **Show Recents** on/off toggle for the Frecency list; footed by the [[Paste permission hint]], which replaced the old footer's redundant toggle descriptions) and a **Providers** section — one navigation row per [[Provider]] that pushes that provider's [[Management page]] (with one umbrella exception: the [[System provider]]'s single row covers Reminders and Events, whose own pages are reached through it — or by typing their names). The top-level rows are navigation only; a provider is enabled/disabled and configured *inside* its own page, not here. Settings no longer holds *only* settings (ADR 0019): each provider's page unifies its settings and its content. The page ends with the [[Build stamp]].
_Avoid_: Preferences sheet, manage screen (the per-provider destination is the [[Management page]])

**Settings command row**:
The single typeable command row every [[Provider]] surfaces, whose main action **deeplinks** to that provider's [[Management page]] (`.openPage(.settings(panel:))`; `panel: nil` opens the top-level [[Settings]] page). For content/capture providers it *replaces the target* of the former management-page command row (typing "custom actions" lands on the Custom Actions page, now settings + content in one); for the previously row-less dynamic injectors ([[Computed]], File Search) it is a brand-new row — so every provider, including a disabled one, is re-enableable by typing its name. The lone exception is [[Settings]] itself, which is **non-disableable** so the recovery path always exists.
_Avoid_: Provider row, config command (it is the "Settings command row")

**Disabled**:
An [[Action]] or provider kind that has been **reversibly hidden** from every surface — typed [[Result list]] rows, the Frecency "Recent" list, the [[Favorites grid]], the outward [[Bridged Action]] set, and the [[Actions widget]] / [[Action control]] picker and render — while its data and configuration are retained. Distinct from **delete** (which destroys): disable is the reversible off-switch, delete the permanent one, and both coexist for user content. It exists at two levels: **kind** (a provider's Enabled toggle, the first entry of its [[Management page]]'s options section) and **instance** (a single Custom Action / Snippet / Shortcut, toggled in that page's actions section; an Indexed Folder gets the same per-row toggle on the File Search page, hiding its files while the grant is retained). A disabled kind short-circuits its instances, and the [[System provider]] adds one **umbrella** level above kind: its Enabled toggle off short-circuits every member kind beneath it (Reminders, Events, and its own direct actions), while the member kinds' own toggles keep working underneath. Fallback **activation** and instance disable are related but distinct: **demoting** a fallback to the [[Fallback list]]'s disabled pool (its red minus) hides it from the bottom region only, leaving the action itself live and name-matchable; **instance-disabling** the underlying action hides it everywhere **and** demotes it out of the enabled list into the pool — so a disabled action is never active, and re-enabling leaves it in the pool until the user promotes it again (it does not restore its old rank). The action's enable/disable toggle appears both on its home page and on the [[Fallback list]] itself. A [[Pile]] entry is deliberately **not** instance-disableable: a deferred query is acted on or kept waiting in results — "kept but hidden" is not a state that data has, so its only verbs are stage and discard. Disabling a pinned action keeps the pin (restored on re-enable) but drops it from the grid without consuming a visible slot.
_Avoid_: Hidden, off, archived, soft-deleted (it is "disabled")

**Management page**:
Each [[Provider]]'s own full-screen page — its **settings page and content surface unified** into one (ADR 0019; formerly a separate per-action settings panel plus a content page). Reached by typing the provider's [[Settings command row]] or from the [[Settings]] Providers list, and addressable on its own so the command row can **deeplink** to it. Two sections: (1) **Options** — the provider's declared settings (ADR 0020: `toggle`, `choice` static or `dynamic` — the latter fed live options by the app, e.g. the EventKit calendar list — and `stepper`), with the provider-level **Enabled** toggle (the [[Disabled]] *kind* switch) as the first entry; and (2) the provider's **actions** — each row an [[Action]] with its own enable/disable toggle (the [[Disabled]] *instance* switch) plus **swipe-to-delete** for deletable actions (permanent built-ins like Save for later / New Snippet are disable-only). Providers with no enumerable instances ([[Computed]], File Search) show only the Options section; the capture providers (Reminders, Events) show their [[Capture step plan]] — a reorderable step double-list — beneath Options. Presents full-screen with its own dismiss affordance — never a partial-height sheet; a bespoke sub-view escape hatch is reserved for options no schema case can express. At **regular** width every management page lays out in the [[Readable command column]] (issue #266) — the clamp on the page's `List`/`Form`, so a toggle sits beside the words that name it instead of a window away; at compact width the page is the full-width one that has always shipped. The **Shortcuts** page is the home for the user's imported [[Shortcut Action]]s: its actions section lists each by name, each row a tap into that shortcut's own settings page, which holds the per-instance **Enabled** switch, the **"accepts input"** toggle (the only way Quickie learns a Shortcut takes input, since import is names-only — and what makes it **fallback-eligible**, entering the [[Fallback list]]'s disabled pool), the optional user-defined **alias** field (issue #198 — one word beside the toggles, no separate editor sheet), and its own **Symbol & Color** appearance row (issues #163, #243) opening the same shared page a Custom Action's editor does, so a Shortcut Action can carry a chosen glyph/[[Action color]] exactly like a Custom Action, defaulting to the kind-derived badge until customized; the row also carries swipe-to-delete, plus a confirmed **Remove all** for clearing the whole imported set at once, and its options section hosts the Sync-Shortcut install/re-sync entry point. There is no manual add — the list is populated solely by the Sync Shortcut import. The **Custom Actions** page is where a [[Custom Action]] is created and edited: its options section hosts the **Browse catalog** navigation row (the [[Catalog]]'s single entry point, the Sync-Shortcut precedent), and its actions section lists each with a per-row enable/disable toggle, swipe-to-delete, and tap-to-edit into the **live-mirroring editor** — a form whose [[Argument]] rows *are* the URL template's `{name}` slots (typing the URL grows/shrinks the rows hard, renaming a row rewrites its `{token}`, and dragging the rows sets the **fill order** the breadcrumb asks in, independent of the URL's order), with Save gated on a named, schemed URL carrying **zero or more** slots (a slot-less URL is a valid static link, ADR 0030); there is no fallback control here — a text-first fill order makes the action fallback-eligible automatically (see [[Fallback Action]]).
_Avoid_: Sheet, manager, Settings panel, Manage screen (it is one page: settings + content)

**Highlighted result**:
The single best result row — `results[0]`, rendered nearest the input and thumb — shown with distinct emphasis so it reads as the default. It is always the nearest-thumb row regardless of how it earned its place (a boosted Calculator/Dynamic result, the best name-match, or the top Fallback when nothing else matches). Pressing **Enter** runs exactly this row's main action. Its Enter intent is signalled two ways: the keyboard's Return key maps to the closest system submit label (e.g. `.search` for a web query, `.go` for a link), and the row itself carries a `⏎`-plus-main-action-glyph hint showing precisely what Enter will do. On Home (empty query) there is no highlighted result and Enter does nothing. Return is the one key a [[Key command]] never redeclares — this is its meaning, keyboard or not.
_Avoid_: First result (ambiguous: first-in-array vs first-on-screen), default row, selected result

**Key command**:
A hardware-keyboard command the launcher claims. It is declared **twice, deliberately**, because listing and binding are separate jobs. The SwiftUI scene's `.commands` does the **listing**: the iPadOS 26 menu bar shows it, discoverable the system way rather than a private key set nothing can describe. A `UIResponder.keyCommands` array on the app delegate does the **binding**: a scene's commands are realized through the *menu* system, which exists on iPadOS and not on iPhone, so the declaration alone leaves an attached keyboard dead there. The delegate sits at the end of the responder chain — far enough out that it needs no wrapper around the launcher's layout, and close enough to nothing that a presented sheet or a navigation controller still gets first refusal on a key. The declared set is **⌘K** (focus the search input), **⌘,** (open the [[Settings]] hub), and **⌘1–⌘4** (run the [[Favorites grid]]'s four cards). A ⌘-digit is **tap-equivalent** to its card: the Action opens verb-first with the typed query cleared rather than seeded as a fallback; an unpinned slot resolves to nothing rather than wrapping. Each key follows its affordance rather than overriding it — while a [[Quick capture]] or the [[Search Files context]] owns the launcher there is no grid on screen and no search field to return to, so ⌘K and the ⌘-digits are no-ops there instead of tearing down a breadcrumb the user is part-way through. ⌘, pushes the hub and nothing else: a key press has no touch behind it, so it records no [[Frecency]] and fires no tactile beat, unlike running the typed [[Settings command row]]. Return is not redeclared — it keeps its [[Highlighted result]] meaning. **esc** is the one contextual key, and the one deliberately *never* declared to the menu bar: an unmodified key claimed app-wide would swallow the system's own escape on every [[Management page]] and sheet, so it is **offered** to the responder chain only while the launcher itself is frontmost — unoffered, the key is not claimed at all and the system keeps its own behaviour. Where it is offered, it **unwinds one layer at a time** — first the typed text of whichever input owns the bottom bar (the query, or a [[Quick capture]] step's), then an active capture, then the [[Search Files context]], and nothing at all on a clean [[Home]]. Each exit routes through the very call its × affordance uses, so the key and the tap cannot drift apart. Standard system shortcuts (⌘C, ⌘V, ⌘A…) are never repurposed — the declared set is asserted disjoint from them. Which keys are claimed and what esc unwinds are Core decisions, so the App only renders the declaration and performs the outcome. Arrow-key navigation of the [[Result list]] is deliberately absent: it needs a highlight model the Core does not have yet.
_Avoid_: Hotkey, key binding, keyboard shortcut (collides with an imported [[Shortcut Action]]), menu item

**Match highlight**:
The bolding of the query letters that found their place in a result's name — the row explaining *why* it surfaced. It appears on every row whose presence a **name match** decided: the ranked name-matches in the [[Result list]] and file rows (both the inline capped rows and the [[Search Files context]]). Boosted rows ([[Computed]]), fallback-region rows, and [[Home]] rows never bold — they never name-matched. When the query appears as a contiguous run of the name, that leftmost run bolds (mirroring the prefix/substring preference of ranking); when its letters only scatter through the name, the first run of them in order bolds. A multi-word query bolds each word's match on its own and shows the union. A **forgiving** (typo) match bolds only the letters that landed exactly where they belong — a mistyped or swapped letter stays plain, since bold means "this letter you typed found its place" (`gthub` → "**G**i**tHub**", `githib` → "**Gith**u**b**"). Bolding is diacritic- and case-faithful (`cafe` bolds the accented letters of "Café"). Under the **single-source rule**, the title bolds only when the *title* was the winning match; when an alias won instead — including a hidden alias like a built-in command's or a [[Pile]] entry's body-as-alias — the title stays plain, and the alias-pill ticket adds the pill-side bolding. It rides each [[Result list]] row alongside the row's region — the two facts a row carries about *why* it is here.
_Avoid_: Match emphasis, query highlight, fuzzy highlight (it is the "Match highlight")

**Alias pill**:
A small, dim, caption-sized capsule sitting inline right after a result row's title, showing the **user-authored alias** its Action carries so it reads as part of the name ("Things 〔th〕"). It is a **memory aid**: it appears on every such row *all the time, query or not*, so the user re-learns the aliases they defined — one pill per row, since the editors collect at most one alias. It rides only Actions whose alias is a user-chosen *name*: a [[Custom Action]] (slotted or static) today, and a [[Shortcut Action]] once Shortcuts gain aliases. Two shapes are carved out because their "alias" is not a name to re-teach: a **built-in command** row (whose aliases — the [[Computed]] row's "calc", "converter" — are matching fodder and rename-insurance; rendering 3–6 permanent pills would bury every command row in chrome) and a [[Pile]] entry (whose sole alias is its entire body text, how a titleless blob stays searchable). **Bolding** is the [[Match highlight]] layered on top under the same single-source rule: when the alias *strictly outscored* the title, the pill's matched letters bold (same alignment as the title) and the title stays plain; when the title won or tied, the title bolds and the pill stays dim. A fallback-region row and a Home row carry no match, so their pills are always dim — the pill **never bolds on a fallback-region row**. The pill rides everywhere the shared result row renders — the [[Result list]] (including the fallback region) and the [[Home]] **Recent** list — but **not** the [[Favorites grid]] cards, a separate compact component. A long title truncates rather than pushing the pill out of the row.
_Avoid_: Alias badge, alias tag, alias chip, keyword pill (it is the "Alias pill")

**Workflow**:
Reserved term, not yet built. A future user-composed chain of multiple Actions, where each Action's output content feeds the next Action's input (validated by content type), authored as visual step-chaining rather than a text DSL. Made possible by every Action declaring typed input/output content from day one. Do not use "Workflow" to mean a single multi-step Action.

**Content type**:
The kind of a value flowing through Quickie — text, url, file, number, date, etc. An item's content type determines which Actions are eligible for it (and their ranking), which secondary actions a result exposes, the **input method** used when it is collected as an Argument (e.g. `date` → an in-place date picker), and — in a future Workflow — whether one Action's output can feed another's input.
_Avoid_: Data type, kind, payload type

**Result content**:
The concrete value or reference a result carries — the thing a [[Secondary action]] operates on — distinct from both its **content type** (the *kind*) and its **main action** (what tapping it does). Either an inline value (a Snippet's or Calculator's text, a static Custom Action's URL) or an edge-resolved reference the app dereferences on demand (a [[Pile]] entry's text by id, a File by bookmark + relative path, a [[Shortcut Action]] by name, a Snippet / [[Custom Action]] (static or slotted) by the stored record's id so the **Edit** verb can open its editor). A command or capture row has **no** Result content, which is what makes it ineligible for secondary actions regardless of its content type (ADR 0017). A Shortcut and a Custom Action are the references carrying no textual value — a Shortcut's name and a Custom Action's id are pure handles for the **Edit** verb, so each is eligible for that verb alone (no copy/share); a static Custom Action, though it carries a real URL to copy/share, likewise keys its Edit off its stored id. Declared per Action, not derived from the main-action outcome (a Shortcut's run outcome is empty yet it declares its name; a Calculator reads as `number` though it copies text).
_Avoid_: Payload, value, content (ambiguous with content type)

**Fallback Action**:
An Action **activated** in the [[Fallback list]]'s enabled section: always surfaced in the result list's bottom fallback region, its point being to **consume the user's typed query as its first Argument** rather than to be found by name-matching. Selecting one **seeds-and-commits**: the query text is committed as Argument 1 through the normal breadcrumb engine — a single-Argument fallback (web search, Save for later, New Snippet, a [[Shortcut Action]] that accepts input) therefore completes in one tap, while a multi-Argument one continues the breadcrumb at step 2 with pill 1 sealed (re-editable like any pill). There is **no fallback flag**: an Action is **fallback-eligible** by *shape* — its first Argument is free text (a date- or choice-first Action has nowhere to put the query) — so every text-first [[Custom Action]], every Shortcut with accepts-input on, the two built-in captures, and the two argument-collecting captures ([[Reminder]] and [[Event]], whose first step is always a free-text title, so the query seeds the title and the breadcrumb continues) are eligible automatically. Eligibility only admits an Action to the Fallback list's disabled pool; the user **activates** it there. Being a fallback is orthogonal to what the Action is — an activated Custom Action or Shortcut is still startable verb-first, where the breadcrumb begins empty. So an enabled fallback whose name or alias matches the query appears **twice**, and both rows are justified because they do different things: a **ranked name-match** row — selecting it starts the Action verb-first, breadcrumb empty at Argument 1 — and the **fallback-region** row — selecting it seeds-and-commits the typed query as Argument 1. The run path tells the two apart by the tapped row's **region** (the row carries it — see [[Match highlight]]), never by inferring it from the action's fallback status; [[Match highlight]] follows suit — the ranked duplicate bolds like any name match, the fallback-region row never bolds. The ranked duplicate ranks by its match quality like any other row (no fallback boost), and an enabled fallback stays out of the Home **Recent** list either way. The single result list interleaves fallbacks with name matches; the user resolves intent by choosing a row, never by a mode toggle.
A fallback promoted to the [[Shelf]] **vacates the bottom fallback region** — it surfaces on the Shelf instead, with the same seed-and-commit tap — while its ranked name-match duplicate keeps appearing under the dual-row rule unchanged.
_Avoid_: Default action, catch-all, fallback flag (retired — eligibility is derived from shape; activation lives on the [[Fallback list]])

**Quicklink**:
*Retired term (ADR 0030) — folded into [[Custom Action]].* A Quicklink was a stored *static* URL with no `{slot}` that opened directly; it is now simply a **slot-less Custom Action** — the same concept with zero arguments. The kept term still names that shape informally: a "static Custom Action" or "static link" wears the link glyph, opens directly, and carries copy/share **and** Edit. The former separate Quicklinks page, storage, and provider are gone; all links live under Custom Actions.
_Avoid_: Bookmark, URL action (use "static Custom Action" / "static link"); do not describe it as a distinct concept from Custom Action

**Custom Action**:
A user-authored Action defined by a **URL** with **zero or more** `{slot}` tokens (ADR 0021, 0030). **With slots**, they become the breadcrumb's ordered, typed [[Argument]]s and the final commit opens the filled URL (e.g. `things:///add?title={…}&when={…}`); such an action is automatically **fallback-eligible** when its first fill-order Argument is free text (no flag; see [[Fallback Action]] — activation happens on the [[Fallback list]], where a newly eligible action waits in the disabled pool). **With no slot**, it is a *static link* (the former [[Quicklink]]): a resolved URL that opens directly, consumes no typed text, wears the link glyph, and is **not** fallback-eligible. Either way it matches by name/alias like any Action — verb-first selection of a slotted one starts the breadcrumb empty at Argument 1 — and because submission opens a URL it hands off to another app or the browser, so it is **not** a [[Quick capture]]. Web search is a default-seeded one-Argument Custom Action, pre-enabled as a fallback (a normal, fully deletable entry); the former "Fallback query" kind is absorbed wholesale into this concept. Custom Actions are **default-seeded** on first run — the templated web search, App Store search, Wikipedia, YouTube search, and Google Maps (pre-enabled as fallbacks), plus the static site links YouTube, Gmail, and GitHub (not fallbacks) — under fixed, well-known ids (the CloudKit dedup convention); each is an ordinary, fully deletable entry, and a deleted seed never re-seeds itself (the [[Catalog]] is the way back). A Custom Action result also carries an **Edit** [[Secondary action]] opening the same live-mirroring editor the Custom Actions page uses. A slotted one exposes Edit **alone** (its URL only exists once filled, like a [[Shortcut Action]]); a static one adds Edit *on top of* copy/share (it carries a resolved URL — the Snippet pattern, for a URL). Every enabled Custom Action is also exposed outward as a [[Bridged Action]]. A Custom Action may also carry a user-chosen **glyph** (the default seeds and every [[Catalog]] install ship one pre-picked) — an SF Symbol picked from a curated, searchable set in the same editor (reusing the choice input method's fuzzy-find furniture) — which replaces its derived *leading* glyph on **every** surface (result rows, the [[Favorites grid]], both widgets, the [[Action control]], its management-page row), rendered with the same tint and weight as a derived glyph so a customized action reads as *specific*, never *foreign*; unset, the kind-derived glyph applies unchanged, and the *trailing* main-action glyph is never user-set — it stays derived from the outcome so it cannot drift from behavior. The same convention carries the [[Action color]]: a curated-palette tint chosen beside the glyph, defaulting to the kind-derived tint.
_Avoid_: URL Action, Template action, Quick Action (an iOS home-screen term), Fallback query (retired — absorbed here), search action

**Action color**:
A per-Action **tint** chosen from a curated palette of ten named tokens — red, orange, amber, green, teal, blue, indigo, purple, pink, graphite — plus **Default**, which is the *absence* of a choice and means today's provider-kind-derived tint (issue #243). It is the [[Custom Action]] glyph's sibling customization, and the two are chosen **together** on one **Symbol & Color** page the editor's single appearance row opens — not a picker each. They compose into one object, the badge, so the page's hero is that composed badge, live: it restyles as swatches and glyphs are tapped, and Back confirms (no auto-dismiss, so a wrong tap is corrected by tapping again). The hero and swatches stay pinned while the glyph gallery scrolls — a preview you cannot see while choosing is no preview — and the gallery keeps the glyph picker's fuzzy search. The selected glyph cell tints itself with the *chosen colour* rather than the app accent, so the gallery echoes the hero. Both halves stay purely opt-in and independent: colouring an action never gives it a symbol, or the reverse. Stored as a **token**, never a raw hex string, so the actual fills stay tuned in one place and a palette revision reaches every stored action at once. The fills are not hand-picked: they are generated by the **same method and tool as the provider-badge ring** (`docs/brand/badge-palette-methodology.md`; issue #178) — OKLCH lightness 0.55, chroma at each hue's gamut ceiling capped at 0.24, flat literals rather than a light/dark pair — because a user-chosen badge and a kind-derived one are the *same badge* and must read as one family. `swift test` pins them to the ring's own white-contrast band (4.4–5.6:1) rather than eyeballing them. The one deliberate departure: the ring leaves the accent and gold arcs empty so an *assigned* badge never reads as a broken accent, while this palette keeps Amber, Indigo, and Purple — a user picking purple is a deliberate choice, not a mis-assignment, and a picker missing the obvious names would read as broken. The token is persisted on the action and syncs through CloudKit exactly like the glyph; a token a build's palette doesn't know — a record synced from a newer one — resolves to Default rather than to a blank, the same degrade path the glyph takes. It tints the **leading badge** on every surface that draws one: result rows, the [[Favorites grid]], both widgets, and its management-page row (where a colour alone is now enough to earn a badge, which previously only a chosen glyph did). It also carries the glass tint of the action's [[Shelf]] button (ADR 0037) — the same hue, held back to what glass can wear, resolved through the one shared rule so a badge and its Shelf button can never disagree. The [[Action control]] has no badge — a Control Center control may only carry a symbol *reference* — so there the token lands on the control template's own tint, the colour Control Center gives it when on; Default passes no tint and keeps the system colouring. The **trailing** main-action glyph is never affected: it stays derived from the outcome, so what a tap does can't be recoloured into meaning something else. The first-run seeds and every [[Catalog]] entry ship a sensible default token (Maps green, YouTube red, GitHub graphite), and the user may override the colour on any action. The four permanent built-in captures ship one too — New Reminder **red**, New Event **indigo**, Save for later **pink**, New Snippet **green** — because they are the [[Shelf]]'s first-run members *and* the only shelvable actions with no editor behind them: whatever they ship with is what that user has. Three take the palette's nearest neighbour to the hue their kind already derives, so each lands a shade along the same arc rather than on a new colour (Save for later's pink stays as clear of the [[Pile]]'s own hue as the crimson it replaces, because a row must never read as the entries it creates; New Snippet's green likewise stays clear of the stored [[Snippet]] it creates). **New Event deliberately departs**: the badge ring seats its hue beside New Reminder's on purpose, as its EventKit twin, which is right in a result row — where a title says which is which — and wrong on the Shelf, where the buttons are icon-only and colour carries the disambiguation. It takes indigo rather than the obvious calendar blue because the palette and the ring are generated from one arc, which makes `blue` byte-identical to the Settings badge — a collision the brand check cannot see, since it reads kind tints only.
_Avoid_: theme, accent, hex, custom color, custom tint, palette entry (the *token* is the noun; free hex is deliberately not offered); also do not confuse with the app-wide light/dark Appearance setting, which this is orthogonal to (a token is one flat colour that reads on both)

**Catalog**:
The built-in, read-only gallery of [[Custom Action]] templates ("catalog entries"), grouped by category — search engines, AI chats, reference & site search, app captures, communication & utilities, and **Sites** (static slot-less links — the former Quicklinks, ADR 0030) — reached via a **Browse catalog** navigation row in the Custom Actions [[Management page]]'s options section. **Install** stamps an entry out as an *ordinary* Custom Action — fully editable, deletable, synced, with **no link back** (no update channel, no managed state) — and **always creates a new row under a fresh id**: the Catalog tracks no installed state, every entry always offers Install, and restoring a deleted action is simply installing again (a new identity — no Frecency revival). Only the first-run **default seeds** carry fixed ids, and that is the seed path's doing, not the Catalog's. Entries whose URL scheme needs a specific app carry a "Requires <app>" note; templates ship in English/US defaults and are edited like any Custom Action after install. Every entry also ships a **default glyph** — the closest *intent* match from the curated glyph set (brand marks do not exist in SF Symbols: a search engine wears the magnifier, a to-do capture the checklist) — shown as the row's leading badge and stamped onto the installed action exactly as if the user had picked it in the editor, where it stays editable and clearable like any chosen symbol. A mailto/SMS catalog entry hands off to another app, so it is *not* a [[Quick capture]].
_Avoid_: template gallery, store, marketplace, presets; also do not confuse with the informal "catalog" used for the engine's indexed action set ([[File Search]]) or the widgets' eligible-action snapshot (ADR 0027) — this Catalog is the user-facing gallery page

**Fallback list**:
The Fallbacks [[Management page]]'s three-section edit surface — the same shape as editing the app row of the native iOS share sheet. The **enabled section** is the user-ordered list of active [[Fallback Action]]s, read **most-important-first** (the top of the page is the fallback nearest the input/thumb; because the Result list renders reversed, this order is reversed when projected into the bottom fallback region); each row carries a red minus that **demotes** it to the pool. The **disabled pool** below lists every fallback-eligible Action not currently active, alphabetical by title — a waiting room, not a ranking, so it is deliberately not reorderable; each row carries a green plus that **promotes** it to the **bottom** of the enabled section (promotion says "available", not "most important"). Membership in the enabled section is the only fact the user sets here — the pool is derived (everything eligible but not enabled) — and nothing on this page deletes anything: deletion lives on an action's home page. An Action that **loses eligibility** (a Custom Action's first argument stops being free text, a Shortcut's accepts-input turns off, a re-sync drops the shortcut) leaves the page entirely with **no memory** of its rank; regaining eligibility re-enters it as a newcomer in the pool. The page reads like the iOS share sheet's app row: the **enabled section** is always in edit mode, so each active row shows a drag **grip** (reorder) beside its red minus and carries **no** toggle; the action's **enable/disable** toggle lives only on the **pool** rows (the same instance switch its home page shows). Disabling an action (there or on its home page) hides it everywhere **and** demotes it into the pool, so the pool holds both not-yet-activated actions (a green plus, ready to promote) and disabled ones (dimmed); re-enabling leaves it in the pool until promoted (no rank restore), and promoting a disabled one re-enables it. The default seeds ship pre-enabled, most-important-first: web search, App Store search, Wikipedia, YouTube, Google Maps; the two built-in captures (Save for later, New Snippet) ship on the [[Shelf]] instead, and are permanent members of the page — demotable between tiers, never removable. Replaces the previous single-list page with per-row disable toggles. Every row across all three tiers leads with the same **provider badge** every other surface renders — the kind-derived glyph and tint, or a Custom Action's/Shortcut's own chosen glyph/[[Action color]] when set — so the page that governs *which* fallbacks run also says *what* each one is at a glance. A third tier sits **above** the enabled section: the **[[Shelf]] section**, its own drag-ordered list forming a promotion ladder (pool → enabled → Shelf). Promoting an action to the Shelf removes it from the enabled section; demoting it from the Shelf inserts it at the **top** of the enabled section (it was important enough to shelve, so it does not fall to the bottom); a pool row can be promoted **directly to either tier** — no forced two-step climb. Losing eligibility prunes a Shelf member exactly as it prunes an enabled one: gone entirely, rank forgotten.
_Avoid_: Fallback settings, fallback order screen (it is one page, "Fallbacks")

**Shelf**:
The horizontal, scrollable row of circular, icon-only Liquid Glass buttons rendered directly **above the input** while the query is non-empty — each a [[Fallback Action]] the user promoted there, each button's glass tinted with its action's [[Action color]]. A tap **seeds-and-commits** the typed query exactly like a fallback-region row; a long-press opens the action's ordinary long-press menu — the *same* [[Secondary action]] + Pin/Unpin menu its result row would show, with the action's **title** as the menu's non-action first row (the disambiguation affordance for icon-only glyphs: the name it can't wear on the button itself). There is no separate reveal gesture and no floating title capsule — one hold, one menu, so a shelved action is no less actionable than the same action in the [[Result list]]. Membership is **purely the user's choice** on the [[Fallback list]]'s Shelf section — there is deliberately no capture-vs-search category anywhere in the model (ADR 0037): any active fallback can be shelved, and shelving removes it from the bottom fallback region. There is **no member cap and no overflow menu**: the row scrolls horizontally, most-important-first from the leading edge, and when members extend past the screen the next button **peeks** partially past the trailing edge — the sizing cue that says "this scrolls" (the iOS share sheet's app-row idiom). The Shelf is hidden entirely on an empty query — it means "ways to use *this* query", so an empty capture is started from the result list or [[Home]], never here. First run ships it as New Reminder, New Event, Save for later, New Snippet, in that order — a default, fully user-editable — each carrying its own shipped [[Action color]], so the row a fresh install opens on reads as four distinct circles rather than four variations on one.
_Avoid_: favorites bar (collides with [[Favorite]]), capture row / save row (no category exists — ADR 0037), quick actions, dock

**Argument**:
A typed or picked value an Action consumes during its lifecycle. An Action declares zero or more. They are collected one slot at a time in the single bottom input field, with the active Action and filled slots shown as a breadcrumb/pill (`[New Reminder] ▸ "buy milk" ▸ …`). Each Argument declares a **content type** that determines its **input method**: the single input region morphs to the right control per step — the keyboard for free `text`, an in-place graphical picker for a `date`, and for a fixed set of options a **fuzzy-find that reuses the matcher and the reversed result list** (type to filter, best match nearest the thumb) — so the user is never typing a value the system could pick. Verb-first selection clears the search query and prompts for the first Argument; noun-first (Fallback) selection **commits** the literal typed text as the first Argument (seed-and-commit — see [[Fallback Action]]).
_Avoid_: Parameter, field, input (ambiguous)

**Input method**:
The input control the single bottom field morphs into for the current Argument, chosen by that Argument's **content type**: the keyboard for `text`, the keyboard in a **numeric variant** (the system number pad) for a `number`, an in-place graphical picker for a `date`, and a fuzzy-find over a fixed option set (reusing the matcher and the reversed result list) for a choice. The number pad is a *variant* of the keyboard method — still the keyboard, only laid out for digits — not a separate method, and like every input method it is derived from the content type, never set by hand. The mechanism that lets one input region serve every Argument type without modes — the user never types a value the system could pick.
_Avoid_: Input mode, control, widget

**Clear button**:
The trailing `✕` inside the single bottom input's Liquid Glass capsule, shown only while the query is non-empty. One tap empties the query and **keeps the keyboard up** — clearing is "start over", not "done", so the next keystroke lands straight in the field. It is furniture of the input itself, not a surface of its own: it rides *inside* the input's glass (unlike the [[Clipboard prefill]] chip, which has its own glass precisely so it can morph in and out of the capsule), and it never resolves anything — it is the manual counterpart of the automatic clear a [[Main action]] performs when it resolves a query. In the [[Search Files context]] it clears the scoped filter text and leaves the context standing; leaving a context is the breadcrumb's job, never this button's.
_Avoid_: Cancel button, dismiss, reset

**Snippet**:
A piece of saved, reusable text whose primary action is **Copy** — canned replies, an address, a template the user pastes repeatedly. Stored in Quickie (SwiftData + CloudKit), searchable as Actions, addable via the Share Extension. Quickie deliberately has no automatic clipboard history (iOS forbids ambient clipboard access).
_Avoid_: Clipboard history, clip, stash

**Pile**:
The collection of raw query texts the user saved to deal with later — "queries I didn't want to process on the spot." Replaces the former Note concept wholesale: there is **no title, no reader, and no compose-editor**. Each **Pile entry** is just a block of text, stored in Quickie (SwiftData + CloudKit) and captured **silently** by the "Save for later" Fallback (no app switch, no confirm step). An entry is an Action in the index, fuzzy-matched over its **body text** (there is no title to match), and its main action **stages** the text: it replaces the input query and re-runs the matcher — the same reinjection move as a [[Shortcut Action]]'s returned output — after which the entry **leaves the Pile** (staging consumes it). On the **Pile page** (reached via a "Pile" command row; aliases "pile", "later", "saved"), tapping an entry **stages** it — the same main action as its result row, popping back to the launcher — and swipe-to-delete discards an entry *without* staging it. The entries are temporary, so their page is **purely content to view and act on** — deliberately *not* the Pile provider's settings page (a [[Management page]] reached from the [[Settings]] Providers list), the one carve-out from ADR 0019's unified shape; per-row removal from the Result list is the eventual first [[Secondary action]] ("Remove from Pile"), deferred with the long-press mechanism. Distinct from a [[Snippet]] (reusable copy-out text, which keeps its title and *copies* rather than *stages*). Besides the silent Fallback, entries also arrive by **auto-save**: an expired [[Pending query]] commits here — no dedupe against existing entries, no [[Frecency]] credit (an auto-save is not a user selection). The provider's settings page holds the single auto-save `toggle`, default on, its copy stating the fixed 30 seconds. Every entry wears its **age** — always shown, as the single coarsest unit ("3w ago") — in the muted subtitle channel of its row on **both** the Pile page and its Result-list row (the same optional-subtitle anatomy a file row uses for its relative path; never opacity, which is reserved for [[Disabled]] rows); the Pile page header carries the entry count and oldest-entry age, and **nothing outside the page advertises either** — the Pile command row stays bare, and there is no badge anywhere. Aging is information, not enforcement: no auto-expiry, no auto-delete (silent destruction of saved text would contradict the [[Pending query]] promise).
_Avoid_: Note, Inbox, notes system, memo; the individual item has no proper noun — say "a Pile entry" or "a saved query"

**Pending query**:
Unresolved text left in the plain root input when the app backgrounds (while the Pile's auto-save toggle is on): snapshotted as `(text, timestamp)` to the App Group defaults at background time and resolved at the next activation — warm foreground or cold launch — by comparing timestamps (ADR 0031). A **plain open** (app icon, app switcher, or a tap on its Live Activity) within **30 seconds** restores it — still mid-thought, now surviving termination too; at or past 30 seconds it commits to the [[Pile]] — moved on — landing on a clean [[Home]] with the flash « Saved "…" for later »; any [[Entry surface]] commits it immediately at any age — "something new *now*", replacing the old silent discard. Only a plain root-launcher query qualifies: a half-filled breadcrumb and the [[Search Files context]] still reset after the window but save nothing — the Pile holds raw query texts only. A Calculator-family query (a math expression, base notation, or unit conversion — the [[Computed]] provider's calculator half) also saves nothing: its answer was the point of typing it, so auto-saving "2+2" would deposit noise, not a kept thought; the exclusion ignores the per-type toggles, since a toggled-off computation is no more worth keeping. A **Live Activity** mirrors the unresolved input itself: it starts on the first qualifying keystroke (already live when the user backgrounds — no request-at-background lag), updates as they type, and ends the moment the query empties, a main action resolves it, or a scoped context takes over; backgrounding only arms its self-dismissal at the window's edge, and a return within the window lets it ride on with the restored query. Compact/minimal Dynamic Island shows generic glyphs only, expanded and Lock Screen show the truncated text with a return arrow, and its tap is a plain open (never `quickie://entry`, which would commit instead). No path silently destroys typed text while the feature is on; toggled off, everything behaves as before — state preserved indefinitely, entry surfaces discard, no activity.
_Avoid_: stale query, draft, autosaved input

**Stage**:
The main action of a [[Pile]] entry: replace the input query with the entry's saved text and re-run the matcher, rebuilding the Result list as if the user had typed it — then remove the entry from the Pile (staging consumes it). Mechanically identical to a [[Shortcut Action]]'s output reinjection; the difference is only the trigger. The user is left "typing" the deferred query and decides what to do with it next. The **Calculator** reuses this reinjection in its main action: a math result **copies-and-stages** — it writes the answer to the clipboard *and* stages it back into the input so the user keeps calculating from it (`2+2` → `4` → `4 * 3`). Unlike a Pile stage it carries a literal value (nothing to resolve, nothing to consume) and reads as a **Copy** row — the copy is the headline, the staging the "also". **Staging follows the answer's kind, not the query's topic**: any *number-valued* Computed answer copies-and-stages — including a [[Date & time]] count ("days until dec 25" → 152), because once the answer is a number it *is* arithmetic, whatever question produced it — while a *terminal* answer (a date, a time, a detected color) is **copy-only**: it is not something to keep calculating with, so nothing is reinjected.
_Avoid_: Open, restore, load, paste (staging re-runs the matcher; it is not a passive paste)

**Quick capture**:
An Action that creates a record from the bottom input *without leaving Quickie* — the family comprising **Save for later** (Quickie-stored, into the [[Pile]]), **Reminder** and **Event** (written to EventKit). Each is silent by default (no app switch) and collects its fields through the breadcrumb, honoring just-in-time permission (ADR 0012). **Save for later** is the one capture that is **not** [[Standalone-runnable]]: its main action *silently* writes the raw typed query into the Pile, so run verb-first with no query it does nothing. **New Snippet** shares the same Fallback shape but *is* runnable — run standalone it opens the Snippet editor (seeded with the empty text), a real verb-first action — as do Reminder and Event, which open the breadcrumb.
_Avoid_: Quick add, capture (ambiguous)

**Standalone-runnable**:
Whether running an Action **verb-first with no typed query** — from an [[Entry surface]], a [[Favorite]] card, an [[Actions widget]] / [[Action control]] button, or a `quickie://run/<id>` deeplink — does something. Two shapes fail it: a [[Pile]] entry (its run *consumes* it, so a bound button dies after one tap) and **Save for later** (its run *silently* writes the absent query into the Pile — nothing to save, nothing to see; detected by its `.saveToPile` outcome, not its kind). Everything else runs to a real effect — including **New Snippet**, whose run opens the Snippet editor, and the argument-collecting captures (Reminder, Event), which open the breadcrumb. The single shared test the standalone surfaces read from so their "is this worth offering?" answer can never drift: an Action is [[Favorite]]-eligible and [[Actions widget]]/control-eligible **iff** it is standalone-runnable, and a row's **Copy action deeplink** ([[Secondary action]]) is offered only when its own run does something (a Pile entry keeps that verb — its run stages, which *is* an effect — so the deeplink is gated on "not Save for later" specifically, not on the full predicate).
_Avoid_: Runnable (ambiguous — everything "runs"), launchable

**Reminder**:
A quick-capture Action that creates an EventKit reminder from the breadcrumb — always a **title**, then whichever of **due date** (with an alarm when a time is given; a date-only due date sets no alarm), **notes** text, **priority** choice (None / Low / Medium / High → EventKit 0/9/5/1), and target **list** the user has turned on, in the order they arranged them (see [[Capture step plan]]). List on asks each time; off routes to a chosen default list. Lives in the system Reminders store, distinct from a **Pile** entry (Quickie-stored deferred query text). EventKit permission is requested just-in-time when the Action is activated, before data entry (ADR 0012).
_Avoid_: Todo, task, alarm

**Event**:
A quick-capture Action that creates an EventKit calendar event from the breadcrumb — always a **title**, then whichever of **start** (a timed start defaults to a one-hour duration; a date-only start becomes all-day; the step off makes it all-day today), **location** text, **notes** text, and target **calendar** the user has turned on, in the order they arranged them (see [[Capture step plan]]). Calendar on asks each time; off routes to a chosen default calendar. Silent by default; a setting instead opens the pre-filled system event editor for final review. EventKit permission is requested just-in-time on activation (ADR 0012).
_Avoid_: Appointment, meeting, calendar entry

**Capture step plan**:
The user's per-capture arrangement of which steps a Reminder or Event collects and in what order — a reorderable two-section list on the provider page (the same On/pool shape as the [[Fallback list]]): an **On** section (ordered, drag to reorder, a red minus turns a step off) above an **Off** pool (a green plus turns a step on). The **title always leads** and is never in the list. The enabled, ordered steps become the breadcrumb after the title, so the plan is the single persisted fact; the disabled pool is derived from the capture's fixed step universe.
_Avoid_: calling it a set of toggles (order matters, and it's one list, not independent switches)

**Clipboard prefill**:
A launch-time offer to seed the input field with the current clipboard contents. Quickie silently checks only whether the clipboard *has text* (metadata, no system banner) and, if so, shows a tap-to-fill paste chip backed by the iOS Paste control — reading the actual content only on tap, never ambiently. Tapping the chip **does raise the iOS paste-permission alert**: the bare system paste control is exempt from that alert, but only when shown untouched, and Quickie deliberately dresses it in the input bar's Liquid Glass (the bare control's opaque platter clashes with it), trading the exemption for the look. That trade-off is accepted, not a bug to fix; the mitigation is the [[Paste permission hint]] — inform the user, don't fight the system.
_Avoid_: Auto-paste, clipboard read; never describe the chip as prompt-free or banner-free (only the *has-text metadata check* is silent — the tap prompts until the user allows pasting in iOS Settings)

**Paste permission hint**:
The footer line under the [[Settings]] app-level section telling the user how to stop the iOS paste-permission alert for good: "To paste without iOS asking each time, set Paste from Other Apps to Allow in iOS Settings.", followed by a tappable **Open iOS Settings** link that deeplinks to Quickie's page in the Settings app (where the *Paste from Other Apps* row lives — the user still flips it to **Allow** themselves). It replaced the footer's former toggle descriptions, which restated what the self-describing toggles already said. Passive and always present — never a popup, banner, or nag (an information popup would fight a popup annoyance with another popup) — and necessarily **blind**: iOS offers no way to read the *Paste from Other Apps* state, so the hint cannot know whether it is still needed.
_Avoid_: Paste tip popup, permission primer (that is the quick-capture pattern, ADR 0012)

**Build stamp**:
The last line of [[Settings]] — `Quickie <version> (<build>) · <short git commit>`, centered in a footer-only section, tappable to copy. It answers "what exactly is installed on this device?" without inferring it from the version number, which moves far more slowly than the builds do. The commit is stamped into the built Info.plist by a `Stamp git commit` build phase (`App/Scripts/stamp-git-commit.sh`), so it always describes the *binary*, never the checkout that happens to be open; a trailing `+` marks a build made from a dirty working tree.

Its whole value is being **current**, so staleness is designed out rather than hoped for. The phase runs last (after the plist lands in the product, before code signing) and is marked always-out-of-date, so even an incremental build that recompiles one file re-stamps — switching commits without touching a source file cannot ship the previous hash. The script rewrites the key unconditionally, stamping `unknown` when git is unreadable instead of exiting and leaving the previous build's value in the reused plist: a confidently wrong commit is worse than none. And because every one of those conditions lives in `project.pbxproj`, where an unrelated Xcode edit could drop or reorder the phase with the build still passing, `App/Scripts/check-build-stamp.py` asserts the wiring and runs as its own CI job.
_Avoid_: Version row, About screen (it is a one-line stamp, not a page or a setting)

**Share Extension**:
The iOS share-sheet entry point that turns a shared **URL** or **plain text** into a stored Action written to the shared App Group store (ADR 0006, 0022). A URL becomes a static [[Custom Action]]; text becomes a [[Snippet]] (the default) or a [[Pile]] entry, chosen in a small **classification sheet** with quick edit. It only advertises for URL and text — images and files are out of scope, and it does not appear in the share sheet for them. Items it writes surface in the app on the next foreground, when the in-memory index is rebuilt from the store. Distinct from a [[Provider]]: it is a *write* surface (a way in), not a source of Actions in the [[Result list]]. (The epic that introduced it, #14, said "text → Snippet or **Note**"; read that as Snippet or Pile — Note was retired by ADR 0018.)
_Avoid_: Share sheet action, importer, Add-to-Quickie extension (it is the "Share Extension")

**Favorites widget**:
The interactive Home-Screen [[Entry surface]] mirroring the [[Favorites grid]]: one button per pinned [[Favorite]], in pin order. A button runs its Favorite's **main action** with as little Quickie as possible: a [[Snippet]] copies **in-place** (no app launch), a static [[Custom Action]] or [[Shortcut Action]] **hands off directly** to the browser / Shortcuts app (a Shortcut's output reinjection still lands back in Quickie, exactly as an in-app run), and an Action that needs input or in-app UI (a [[Quick capture]], a slotted [[Custom Action]], [[Search Files context]]) opens the app **pre-selected** — verb-first, breadcrumb at Argument 1, as if its Favorite card had been tapped on [[Home]]. A button whose Favorite no longer resolves degrades to the clean focused Home, never an error (ADR 0025).
_Avoid_: Interactive widget (say which), quick actions widget

**Actions widget**:
The second interactive Home-Screen [[Entry surface]]: the same 2×2 grid as the [[Favorites widget]] — glyph-only cells in small, titled cells in medium, at most four — but showing a **user-chosen** list of Actions instead of the pinned four. The list belongs to the placed widget instance itself, chosen in the system Edit-Widget sheet (no in-app page holds or mirrors it, and each placed instance carries its own list) as **four ordered slots**, each a single-pick from the catalog — not one multi-select list — so the picker shows one item at a time, the choice is inherently capped at four, and the order is set by which slot holds each action; eligible is **every enabled Action that is [[Standalone-runnable]]** — every enabled Action except a [[Pile]] entry (staging consumes it, so a button bound to one would die after one tap) or **Save for later** (its silent Pile write does nothing without a query; New Snippet stays eligible, since it opens the editor; issue #140) — and [[Disabled]] already hides an action from every surface. A slot left empty is skipped; the filled ones pack toward the front of the grid. Buttons execute exactly as [[Favorites widget]] buttons — the same three-way split, the same Frecency outbox. An unconfigured instance renders a one-line long-press invitation whose whole surface deep-links to a clean focused [[Home]]; a chosen action that no longer resolves (deleted or [[Disabled]]) drops from the grid, its slot degrading to the dashed empty-cell tap target — never blank, never inert, never an error.
_Avoid_: Custom widget (collides with [[Custom Action]]), Launcher widget, configurable Favorites

**Action control**:
The configurable Control Center control that runs **one user-chosen Action**, picked in the control's configuration from the same eligible set as the [[Actions widget]]. Activating it opens Quickie and runs the action **tap-equivalently** (through the shared inbox door, `quickie://run/<id>`): a [[Snippet]] copies, a static [[Custom Action]] opens the browser, a [[Quick capture]] opens its breadcrumb — each the correct outcome, its [[Frecency]] credited by the app's ordinary run path. Unlike the [[Actions widget]] it does **not** perform the three-way split (in-place copy / direct hand-off / open): a Control Center control body is a single, non-branching template (WidgetKit's `ControlWidgetTemplateBuilder` has no `buildEither`), and a single intent can't span the lanes (one `perform()` has one return type, and `openAppWhenRun` is static), so the always-open tap-equivalent run is the one path that serves every eligible action. The configured control wears its action's own glyph and title in Control Center; unconfigured or stale (deleted or [[Disabled]]) it falls back to the app glyph and opens a clean, focused [[Home]] — never inert, never an error. Coexists with the static Quick Capture control (a separate gallery entry).
_Avoid_: Run-action control, shortcut control, custom control

**Entry surface**:
A system surface outside the app that gets the user into Quickie fast — the Home/Lock Screen deep-link widget, the interactive [[Favorites widget]] and [[Actions widget]], the Control Center controls (Quick Capture and the [[Action control]]), and the Action Button. The open-focused surfaces express "I have something new to type *now*": they always land on a clean, focused [[Home]] — a [[Pending query]] is committed to the Pile at any age (never silently discarded, while auto-save is on) and a half-filled breadcrumb abandoned — whereas returning via the app icon, app switcher, or the Pending query's Live Activity is a **plain open**, resolved by the 30-second window instead. Distinct from the [[Share Extension]] (a write surface, not a way in for typing).
_Avoid_: Launcher widget, shortcut surface, entry point (ambiguous with code entry points)

**Provider**:
A source that contributes Actions to the result list. Every Action originates from exactly one Provider. Providers are either Indexed or Dynamic.
_Avoid_: Source, Extension (collides with iOS app extensions), plugin

**System provider**:
The umbrella [[Provider]] grouping Quickie's OS-integration actions. Its [[Management page]] leads with a **cascading** Enabled toggle (see [[Disabled]] — off silences every member kind), then two navigation rows pushing the **Reminders** and **Events** pages (their options, [[Capture step plan]], and typed [[Settings command row]]s survive intact — only their top-level [[Settings]] rows fold into this one), then its own actions section with one permanent, disable-only built-in: **Open iOS Settings** (no arguments — opens Quickie's page in the Settings app, the only target iOS exposes; a query-driven "search Settings" was investigated and is infeasible, publicly or privately). Reminders and Events remain full Providers in their own right; System is a grouping, not a merge. **App Store Search** is deliberately *not* a System built-in but a default-seeded [[Custom Action]] (`itms-apps://…/search?…&term={query}`, pre-enabled as a fallback beside web search): its target is a slotted URL, so it fits the Custom Action model, is editable and deletable, and will join the [[Catalog]] (#143) — and it runs through the proven breadcrumb path instead of a System action's routing (issue #144; ADR 0029 Update).
_Avoid_: OS provider, built-ins provider, merged capture page (the sub-pages are linked, not merged)

**Indexed Provider**:
A Provider whose Actions are a known, enumerable set, pre-indexed for fuzzy search and re-indexed only when its underlying data changes (Snippets, Custom Actions, Shortcuts, favorites, built-in commands). Queried from the in-memory index per keystroke.

**Dynamic Provider**:
A Provider that computes Actions on the fly from the current query and is never in the fuzzy index ([[Computed]] — math, unit conversion, and [[Detected result]]s — File Search, Web Search / Fallbacks). Queried live per keystroke (debounced, cancellable, may be async), and decides for itself whether it applies to the query.

**Computed**:
The **boosted-dynamic** [[Provider]] formerly named Calculator — the provider whose rows are derived from the query text *itself* rather than matched by name: a math result, a unit conversion, a [[Date & time]] answer, and the [[Detected result]]s (URL, phone number, email address, hex color). The math capability also reads **base literals**: `0x`/`0b` numbers inside arithmetic (`0xff + 1`), explicit base conversions (`255 to hex`, answering prefixed — `0xFF` — so the staged text stays unambiguous), and a bare prefixed literal alone firing its decimal row — a prefixed literal is an explicit notation act, not a bare number, so the inert-bare-number principle survives. There are **no bitwise operators**, and `^` stays power. The **unit converter** reads and writes **compound imperial length** the way people say heights (issue #215): `5'11"`, `5'11`, and `5 ft 11 in` all parse as feet+inches, and a length conversion **to `ft`** answers compound — "180 cm to ft" → "5 ft 10.9 in" (inches to one decimal), because nobody thinks in decimal feet — while every other target, `to in` included, stays plain decimal; the staged compound answer re-parses as compound input, so the row round-trips. Feet+inches only — stone+pounds and pounds+ounces were skipped. "Calculator" survives as the informal name of its math capability (and as the persisted provider id — renaming the stored identity would re-key kind-level state), but the provider the user sees — the Providers list row, the [[Management page]] title, the [[Settings command row]] — is **Computed**, with "calculator", "converter", and "detector" kept as typed aliases so the rename strands no one. Its options section holds **seven per-type toggles** — Math (which also gates the base-literal grammar), Unit conversion, Date & time, URLs, Phone numbers, Email addresses, Colors, all default-on — beneath the provider-level Enabled switch; like File Search it has no enumerable instances, so no actions section.
_Avoid_: Calculator provider (the provider is Computed; Calculator names only the math capability), Detector (the rejected standalone provider — ADR 0032), Smart input

**Date & time**:
The [[Computed]] capability answering date and time queries, in four grammar families: **relative arithmetic** ("3 weeks from friday" → a date; a bare weekday means the nearest future occurrence, today included), **until/since counts** ("days until dec 25" → a number), **timezone conversion** ("9am PST in tokyo" → a time), and **timestamp decode** strictly behind an explicit trigger word ("unix 1735689600" — a bare digit run stays inert, preserving the bare-number principle). Answers obey the [[Stage]] rule — staging follows the answer's kind: a number-valued answer copies-and-stages exactly like math (`.number` content), a date- or time-valued answer is **copy-only** with `.date` content, formatted per device locale. The grammar is **dual-accept** (ADR 0036): English always parses, and the device language's hand-rolled keyword table (French, Spanish, and German at launch; weekday and month names from the system calendar's localized symbols) layers on top — the same tables localize the unit-conversion connectors. Gated by its own Date & time toggle in the Computed options section.
_Avoid_: Date math (partial — the capability spans conversions too), natural-language dates (that is the deferred capture-seeding concept, a different mechanism), smart dates

**Detected result**:
A [[Computed]] row produced by recognizing the query as a *value*: it fires only when the **whole trimmed query** parses as exactly one URL, phone number, email address, or hex color (a single trailing punctuation mark tolerated) — never on a substring of longer prose, keeping every boosted row justified as "you typed a thing, here's the thing". Bare domains count as URLs: someone who types exactly `apple.com` means *go there*, and the web-search fallback stays one tap away. A URL yields one **Open** row and an email one **Email** (mailto compose) row; a phone number yields **two** rows — **Message** nearest the thumb (the [[Highlighted result]]: a mis-Enter should text, never place a call) with **Call** above it — because call and text are co-equal intents and nothing essential hides behind a gesture. A hex color (`#`-required: `#f60`, `#ff6600`, `#ff6600cc` — a bare hex run without `#` is not a color, it fails the never-a-guess bar) yields one **Copy** row, verb-titled like its siblings, its swatch tinting the leading glyph; a color is terminal, so the row is copy-only per the [[Stage]] rule. Street addresses are deliberately **not** a detected type: without a system detector (excluded for platform-portability) an address regex cannot meet the never-a-guess bar. All are boosted like a math result, resolve the query when run, and carry a bare value as [[Result content]] — the universal copy/share menu, no Edit, exactly a Calculator result's manners. An ambiguous query (`555-1212` reads as phone *and* math) may fire rows from several interpretations at once — separate rows, separate toggles, the user picks; there is no arbitration logic.
_Avoid_: Detection row, smart suggestion, data detector (the mechanism, not the concept)

**Home**:
The empty-query state shown the instant the app opens: the Clipboard prefill chip (when applicable), a **Favorites grid** pinned at the top of the screen over a progressive-blur band, and a Frecency "Recent" list that scrolls *under* that band. The tap-without-typing fast path. On the first keystroke the Favorites grid disappears and the live Result list takes the full height, still scrolling under the same blurred top band. Before the user has pinned or used anything there is nothing to show, and Home falls back to its **pre-anything** form: the [[Brand mark]], the "Start typing" placeholder, and the [[Hint line]] (ADR 0034).
_Avoid_: Landing, start screen, default view

**Living backdrop**:
The field the whole launcher sits on, and the thing its Liquid Glass chrome — the input bar, the [[Shelf]], the Clipboard prefill chip, the [[Favorites grid]] — refracts (ADR 0010): a subtle purple mesh gradient, adaptive to light/dark, that drifts very slowly on [[Home]] and stands still the moment a query exists — alive at rest, calm in use (ADR 0034). Static under Reduce Motion and Low Power Mode. The [[Highlighted result]]'s gold hero glow is **not** backdrop content: it belongs to the highlighted row and is clipped to it, because a glow behind the list bleeds behind the neighbouring rows.
_Avoid_: Wallpaper, animated background, quiet backdrop (the pre-living static gradient it replaces)

**Readable command column**:
The single centred, ~680pt-wide column the launcher's command surfaces lay out inside on a **regular-width** window — a full-screen iPad, or a Stage Manager window wide enough (ADR 0039). The surfaces are the input bar, the [[Shelf]], the Clipboard prefill chip, the [[Result list]]'s rows, [[Home]]'s [[Favorites grid]] (which also picks its column count from the same policy) and Recent list, the [[Search Files context]]'s rows and breadcrumb, and a capture's breadcrumb crumbs and bottom bar; the column's edge stands in for the window's edge, so each keeps exactly the inset off it that it keeps off an iPhone's screen edge (12pt for a row's or the input bar's glass, 16pt for a breadcrumb's crumbs). At **compact** width — iPhone, iPad Split View, a narrow Stage Manager window — there is no column and the layout is the full-width one that has always shipped. The switch is the horizontal **size class, never the device idiom**, so the same window dragged narrow reverts and dragged wide returns, with nothing rebuilt in between. Only *content* clamps: the [[Living backdrop]] and the progressive-blur bands still span the whole window, since a band stopping at the column would draw its two edges as hard lines. The width and the switch are one pure rule in QuickieCore (`CommandColumn`), not a number per view — a column the results share but the input bar misses by 8pt is worse than none, because the whole effect is *one* edge running down the screen. The pushed [[Management page]]s lay out in the **same** column rather than one of their own (issue #266): a grouped row whose label sat at one window edge and whose toggle sat at the other is the same defect the launcher had, so the clamp rides each page's `List`/`Form` — the list's own margins are then measured against the column, carrying every row, header and separator in with them — and the page restates its grouped background outside the clamp, since it has no [[Living backdrop]] to be the full-bleed layer. The editor sheets are not clamped and do not need to be: they present narrower than the column, and a cap only ever subtracts. How small or large the window itself may get is the [[Launcher window]]'s, whose declared floor sits under this column and whose declared default sits over it.
_Avoid_: Content column, iPad layout (the switch is size class, not iPad), max width — as names for the **column**. Its *measurement* is the readable width (`CommandColumn.readableWidth`), which is a different thing and keeps that name.

**Launcher window**:
The resizable rectangle the app lives in on iPadOS 26, and the two sizes it declares about it (`LauncherWindow`; ADR 0041). The **floor** — 320×320 — is the smallest window the launcher is still a launcher in: 320 wide is the narrowest canvas iOS has ever handed the compact layout (the 4" iPhone's, and Slide Over's), 320 tall the shortest that still holds the input bar, the [[Shelf]] and the [[Highlighted result]] together. The **default** — 880×1000 — is the [[Readable command column]] plus a 100pt margin on each side, so a fresh window opens at regular width rather than showing the iPhone layout on a 13" canvas. The floor sits *under* the column and the default *over* it, which is the whole relationship between the two policies: a window dragged across its entire legal range only ever lands in one of the two layouts that are tested. The floor is deliberately no roomier, because the system's own tiling produces a 372pt-tall quadrant on an iPad mini and a 320pt-wide Slide Over panel, and refusing a window the system hands the app is worse than the drag it would prevent. Resizing is **non-destructive** by construction rather than by handling — every layout decision downstream is a pure function of the size class, so a window dragged narrow and back wide returns to the layout it left.
_Avoid_: Screen, display (on iPad the window is only sometimes either — see [[Keyboard lift]]), window size (the *sizes* are the floor and the default; the window is the thing)

**Keyboard lift**:
How far the [[Home]] input bar rides above the bottom of the app's **window** so it sits exactly on the keyboard's top edge. Driven by hand rather than by the system's keyboard avoidance, which is switched off for the launcher: only a manual lift can **hold** its inset when a row's long-press context menu transiently resigns first responder (the list must not reflow under the menu) and still follow the finger through an interactive swipe-dismiss. All of it is measured in the window's coordinate space, never the display's — on iPad the window is only sometimes the whole display (Split View, Slide Over, Stage Manager, free resizing), and a keyboard is only *docked* when it is as wide as the window and reaches its bottom edge; a floating or split keyboard is detached and lifts nothing, and a hardware keyboard's shortcuts bar lifts the bar by its own thin height (ADR 0040). It is **held** — deliberately not released — for exactly one departure: a row's long-press menu dropping the keyboard, so the result list cannot reflow out from under the open menu. Every other departure drops the bar to the window bottom, including iPad's dedicated dismiss key. The two post an identical notification, so the app *reports* the menu rather than inferring it. The [[Living backdrop]]'s hero glow rides the same value, so the glow lands where the bar is.
_Avoid_: Keyboard inset, keyboard avoidance (the system behavior this replaces), keyboard height (what the keyboard covers of *this window* is the point)

**Pointer hover**:
The system highlight that slides under a trackpad or mouse pointer and morphs to the shape of whatever tappable element it is crossing — on iPadOS 26 the *primary* signal that a thing can be clicked, the way a cursor change is on a Mac (issue #263). Every control in the launcher carries it: the [[Result list]]'s rows and [[Home]]'s Recent rows and [[Favorites grid]] cards, the [[Shelf]]'s buttons, the input's [[Clear button]] and the Clipboard prefill chip, a capture's tappable crumbs, choice rows, commit button and ×, the [[Search Files context]]'s rows and ×, and a confirmation toast while it has somewhere to go. The rule is **exactly the controls, and only the controls**: an element that lights up and then does nothing when clicked is worse than one that never lit up, which is why the two elements that are only *sometimes* controls stay dark the rest of the time. A capture's inert crumbs — the current step, and the not-yet-reached steps past the next one — read the same `CrumbTap` verdict that decides whether they are buttons at all, and a copy toast, which is a passing notice rather than a control, hovers only when it carries a URL to open. Each element hovers in the shape it actually draws (a row's 25pt-radius pill, a Shelf button's circle, a crumb's card), never a bounding rectangle, so the highlight can't invent corners the element doesn't have. It exists only while a pointer does: with a finger, nothing about the launcher changes. Settings and the [[Pile]] are `List`s and get the platform's own row hover for free — this is about the launcher's hand-built glass chrome, which gets none by default.
_Avoid_: Mouseover, rollover, focus ring (focus is the keyboard's, a different signal — see [[Key command]]), pointer effect (the API's word, not ours)

**Brand mark**:
The app icon's orbital Q — the same custom SF Symbol every [[Entry surface]] renders — drawn on [[pre-anything Home]] above the placeholder, painted in the brand's trail ramp (the icon's lavender whitening toward the release on dark; the same axis one step lighter on light, where the icon's own ramp would erase itself against the background — ADR 0033). The one place inside the app that says whose app this is, and the reason the mark's symbolset is shared by the app and widget targets rather than owned by the extension: the mark on the Home Screen and the mark inside must be the same mark.
_Avoid_: Logo, app icon (the icon is the Home Screen artwork; the mark is the glyph isolated from it), splash

**Hint line**:
The single quiet line under [[pre-anything Home]]'s placeholder, rotating slowly (a ~7s dwell, a slow crossfade) through instructive examples — "Try 2+2" · "Paste a link" · "Find a file" · "Jot something down" · "Add a reminder" · "Add an event" · "Call a number" · "Search the web" — **one capability per hint** (never app launching: Quickie is not a launcher, ADR 0001). The order is randomized as a **shuffle bag**, not a fixed cycle (a canned reel the eye tunes out) and not independent random draws (which would let one capability recur while another never showed): each pass is a fresh shuffle of the whole set, so every capability is seen once per pass, never twice in a row. It opens on the arithmetic hint — the fastest way to say "not an app list" — which is also the single static hint shown when the line is frozen. It is how Quickie says what it accepts without a wall, a tour, or an empty-state paragraph (ADR 0012 forbids all three), and the one-capability-per-hint rule is the whole point: several phrasings of one trick would teach nothing. It only ever *suggests* — every hint is something the user could literally type — which is why it is a separate element from the placeholder, the instruction, which never changes. Rotation is an enumerated moment in the animation budget (ADR 0010), the specific moment introduced by ADR 0034 — the only one with nothing the user just did behind it, so it is tuned to *lose* an attention contest with the input rather than keep up with it. Under Reduce Motion or UI test the line is **frozen** to a single static hint rather than fading faster, because the rotation *is* the motion and there is no user action underneath it to preserve.
_Avoid_: Tip, tooltip, coach mark, onboarding, placeholder (the placeholder is "Start typing" and is a different element)

**pre-anything Home**:
[[Home]] before the user has pinned a Favorite or used any Action — no grid, no Recent list, nothing of the user's own to show. Not a state to be fixed but where every user necessarily starts, and the only screen in the app that is empty *by definition*; that space is what the [[Brand mark]] and the [[Hint line]] spend (ADR 0034). The three of them read top to bottom as who, what to do and what is worth typing, and they are **placed** as one block at the centre of the band between the top of the window and the input bar they introduce — measured from that band's own height, not left to emerge from the space either side of them, which on a short-and-wide window put the block a tenth of the band too high (ADR 0041).
_Avoid_: Empty state, zero state, first run (nothing here is once-only — it returns whenever Home has nothing to show)

**Favorites grid**:
The grid of small Favorite cards pinned at the top of Home over a progressive blur. Shows **at most four** Favorites, in pin order; it is the launch-time, tap-without-typing surface. Visible only on Home — it vanishes the moment the user starts typing, ceding the screen to results. Its **column count** is part of the [[Readable command column]] policy (`CommandColumn.FavoritesGrid`, issue #265): **2×2** at compact width — the iPhone layout, unchanged — and **one four-across row** inside the column at regular width, since the cap and the regular-width row are the same four. The count follows the window's size class and *nothing else*, least of all how many Favorites are pinned: the row is fixed and fills left to right, so one pinned Favorite draws the same card as one of four rather than a slab stretched across the empty slots. Replaces the earlier horizontal Favorites chip row.
_Avoid_: Favorites row, favorites bar, 2×2 grid (only compact width is 2×2)

**Favorite**:
An Action the user has manually pinned. Capped at **four** (one full [[Favorites grid]]); a fifth pin is refused until one is unpinned. Favorites appear in the Favorites grid on Home, receive a ranking boost in Results, and are exposed outward as [[Bridged Action]]s. Every Action is pinnable **except one that is not [[Standalone-runnable]]** — a [[Pile]] entry (its main action consumes it via [[Stage]], so a pin would outlive its target on first use, a ghost card invisibly holding a grid slot) and **Save for later** (its silent Pile write does nothing run without a typed query, so a pinned card would do nothing; New Snippet stays pinnable — it opens the editor; issue #140). Those rows offer no Pin item, and reconciliation prunes any such pin an older build allowed.
_Avoid_: Pinned, starred, bookmark (bookmark means a static Custom Action here)

**Bridged Action**:
An [[Action]] exposed *outward* through the App Intents bridge (ADR 0009, 0024) as a value of the single parameterized App Shortcut — the set is **derived**, never hand-curated: the union of the user's [[Favorite]]s and [[Custom Action]]s, minus anything [[Disabled]], refreshed whenever pins or Custom Actions change. Invoking one from Siri / Spotlight / the Action Button is **tap-equivalent**: the app opens and behaves exactly as if the user had tapped that Action's result row (a Favorite runs its main action; a Custom Action starts its breadcrumb at Argument 1). A bridged reference that no longer resolves — unpinned, deleted, or disabled since the system last synced — degrades to opening the app on [[Home]]. Distinct from the four **headline App Shortcuts** (Quick Capture, [[Pile]]'s Save for later, [[Reminder]], [[Event]]), which are static phrase-invoked verbs, not members of this set.
_Avoid_: Exposed action, exported action, dynamic shortcut (Apple's mechanism, not the concept)

**Frecency**:
The frequency × recency ranking signal derived from a user's past Action selections. Drives the auto-suggested list on Home and boosts ranking in Results. Distinct from Favorite (which is manual).
_Avoid_: Recents, history, MRU

**Shortcut Action**:
An Action that runs one of the user's iOS Shortcuts by name, via x-callback-url. Quickie opens `shortcuts://x-callback-url/run-shortcut` with `x-success` pointing back at `quickie://`; on `x-success` Quickie **reinjects the returned output as the new query text** — the matcher re-runs over it and the Result list rebuilds as if the user had typed it, so the user decides what to do with it next. Reinjection is unconditional on success: non-empty output gives the user something to act on, and empty output clears the field back to a clean Home ready for a fresh query. Running the shortcut clears the query like any [[Main action]], and the clear is **final**: `x-error` flashes a failure toast and `x-cancel` is a silent no-op — neither restores the cleared text, because the callback may land after the user has started typing something new, and a restore would stomp it. This is the deliberate poor-man's precursor to [[Workflow]] (no content-type validation, no declared next step, just text back into the single input), not the Workflow feature itself. The returned output therefore lives in inbound URL-scheme handling, not in an `ActionOutcome` payload. A Shortcut row also carries an **Edit** [[Secondary action]]: its long-press menu deeplinks into the Shortcuts app's editor for the shortcut by name via `shortcuts://open-shortcut` — the same name-keyed identity the run path uses, so no Apple UUID is needed. Opening the editor is fire-and-forget (no `x-callback-url`, no returned output), and since a runnable shortcut has no text, Edit is its only secondary verb. Registered **only** by bulk import via the [[Sync Shortcut]] — there is no manual one-by-one add path (dropped from #13; see ADR 0007), so a user who has never run the Sync Shortcut has zero Shortcut Actions. iOS forbids enumerating the user's Shortcuts through any API, which is why the companion-shortcut import is the sole on-ramp. Every freshly imported Shortcut Action starts instance-[[Disabled]]: a bulk import must never flood results, so the user opts in the shortcuts they actually want from the Shortcuts page, while a re-sync's survivors keep whatever enablement they already have (and, identity being the name, a renamed or re-added shortcut arrives disabled again). A Shortcut Action may also carry **one optional user-defined alias** — the same single-alias convention a [[Custom Action]] uses — edited on the shortcut's own settings page (the alias field sits beside the Enabled and "accepts input" toggles, no separate editor sheet for one word). The alias behaves like any Action alias: the matcher scores it alongside the name, so typing it surfaces the shortcut, and the row wears it as a dim [[Alias pill]] (bolded when the alias strictly outscored the title, per the single-source rule). It rides the same name-keyed store as `acceptsInput`, so it survives a re-sync the same way — a survivor keeps its alias, a name absent from the payload drops with it, and a renamed shortcut (delete + re-add, since identity is the name) loses its alias, the same documented trade-off as the toggle. A Shortcut Action may likewise carry its own **glyph** and [[Action color]] (issues #163, #243) — the same opt-in customization a [[Custom Action]] carries, chosen on the shortcut's own settings page's Symbol & Color row (the *same* pushed page the Custom Action editor uses, not a second one), replacing its derived badge on every surface a Shortcut Action's row appears (result rows, the [[Favorites grid]], both widgets, its management-page row, the [[Fallback list]] page). Unset, the kind-derived badge applies unchanged. It rides the same name-keyed store and survives a re-sync exactly as the alias does — a survivor keeps it, a renamed shortcut loses it.
_Avoid_: Shortcut command, automation

**Sync Shortcut**:
A Quickie-provided iOS Shortcut the user installs and runs manually. It calls the Shortcuts `Get My Shortcuts` action to collect the names of all the user's shortcuts and returns them to Quickie via the `quickie://` URL scheme, populating the user's Shortcut Actions. Re-run to re-sync; there is no background/automatic refresh.
_Avoid_: Importer, bridge shortcut

**Indexed Folder**:
A folder the user has explicitly granted Quickie access to (via the document picker), persisted as a security-scoped bookmark. Grants are managed on the **Indexed Folders** [[Management page]] — a typed "Indexed Folders" command row (aliases "folders", "file access") opens a full-screen list with per-row removal and an **Add Folder** button that presents the document picker in folder-selection mode. Because bookmarks are opaque and device-specific, grants are stored **device-locally and never synced** (ADR 0016), and a grant whose bookmark no longer resolves is **pruned** rather than left as a dead row. File search is bounded to the union of Indexed Folders — iOS forbids whole-filesystem or global indexing. Filenames within them are indexed for fuzzy matching; results open via QuickLook / share / open-in-place.
_Avoid_: Search scope, watched folder, library

**File Search**:
The **Dynamic Provider** that fuzzy-matches filenames within the union of Indexed Folders. Unlike an Indexed Provider — whose whole catalog the SearchEngine matches and ranks centrally — File Search **owns its own filename index and prefilters it itself**, so a large file set never floods the central catalog, Home, or Frecency. Its handful of survivors are then **scored and placed in the ranked region by match quality** — *not* auto-floated to the top like the Calculator, so an exact command name still outranks a fuzzy filename hit. This makes File Search a **ranked-dynamic** provider (competes on score) as opposed to the Calculator's **boosted-dynamic** behaviour (type-triggered, floats top). Surfaces two ways: **inline-capped** (up to ~3 rows, only on contiguous substring-or-better matches — scattered and typo hits stay in the context, ADR 0035 — while typing a normal query) and the **Search Files context** (uncapped; see below). A file result carries only its Indexed Folder's bookmark identity plus the file's relative path; the app resolves that to a security-scoped URL and opens it — Core never touches the filesystem.
_Avoid_: Spotlight, file provider, file index (that is the data, not the Provider)

**Search Files context**:
The dedicated, uncapped file-browsing surface, entered by **selecting a "Search Files" Action row** — never a chrome mode toggle. Once selected, the input scopes to the file index alone (shown as a breadcrumb, `[Search Files] ▸ …`), full-height, and every keystroke filters only filenames. This keeps faith with the Result list's "intent is resolved by choosing a row, never by a mode toggle": the "dedicated mode" is a selected-Action context reusing the breadcrumb model, not a UI mode. Distinct from the ongoing input filter it maintains, it never *commits* a value the way an Argument does — it is a live scoped filter, not an Argument slot.
_Avoid_: File mode, search mode, files tab
