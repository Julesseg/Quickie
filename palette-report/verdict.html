Verdict: reject

The palette layout is better than today's in the state it was designed for — with a hardware keyboard the query, its answer and the ranked rows sit at eye level instead of huddled in the bottom third under an empty canvas, and rank-0 adjacency survives the inversion (the highlighted result sits directly under the field instead of directly over it).

The mode is what fails, on three counts:

  1. The flip has no interpolable intermediate. Docked renders rank 0 last, palette renders it first — every row is reversed, not shifted, so there is nothing for an animation to travel along. Filmed at the real motion budget, the transition is the input bar moving through the result list while two differently-ordered copies of it crossfade: several rows on screen twice, ~26% of the screen in motion. No choice of spring fixes that; the layouts share no geometry.
  2. The trigger cannot be tested anywhere we build. With a hardware keyboard attached iPadOS posts no keyboard notification at all, so the obvious signal is silent — the absence of a keyboard is not a keyboard event. The signal that works, GCKeyboard.coalesced, is unavailable in the simulator; and XCUITest raises the software keyboard to type, which is the condition the mode is defined by the absence of.
  3. Home gets worse. The Favorites band is pinned to the top, so the field lands under it with the rest of the window empty — the first thing a hardware-keyboard user sees.

Recorded as ADR 0041 — No palette mode: the launcher does not change shape under you. The empty-canvas problem the audit found is real and stays open; this rejects inverting the layout as the answer to it, not the observation.
