Quickie on iPad
UI audit, prototype & recommendations

Audited on an iPad Pro 13″ (M5) simulator, iPadOS 26.3 — every screen exercised by a scripted XCUITest walk, in portrait and landscape. Verdict: the app is fully functional on iPad but every surface is the iPhone layout stretched to fill the window. A working prototype (branch prototype/ipad-ui-audit) fixes the core issue — the full-bleed command surfaces — with one ~20-line, size-class-driven modifier applied at six sites.

1 · TL;DR

The one structural problem: nothing in the codebase knows about width. There is not a single horizontalSizeClass read, width clamp, or adaptive grid in any Swift file — so the input bar, result rows, Favorites, breadcrumbs, and settings forms all stretch edge-to-edge across 1,376 pt of landscape iPad. A result row puts its icon and its chevron ~1,300 pt apart.

The one structural fix: a centered, readable-width command column (~680 pt) on regular-width windows — prototyped, built, and screenshotted below. Size class (not device idiom) is the switch, so Split View and narrow Stage Manager windows correctly keep the iPhone layout.

Beyond layout, the two big gaps for a launcher on iPad: hardware-keyboard support (no ⌘K, no arrow-key navigation, no esc — iPad launchers live on the keyboard) and keyboard-avoidance math that assumes window = screen (UIScreen.main), which breaks in Split View / Stage Manager / iPadOS 26 windowing.

2 · Method

  • Built and installed the app on the iPad Pro 13″ (M5) simulator (iPadOS 26.3). The project already targets iPad (TARGETED_DEVICE_FAMILY = "1,2", all four orientations enabled) — it runs natively, no compatibility mode.
  • Drove every reachable surface with a throwaway XCUITest (App/QuickieUITests/IPadExplorerUITests.swift): Home (placeholder and populated), ranked results, calculator, Settings hub + all eight provider pages, both editor sheets, the catalog, Search Files, the Reminder capture flow (title → list → date), Pile — in portrait, key screens again in landscape.
  • Cross-checked against Apple's current guidance: HIG (Layout, Designing for iPadOS, Multitasking, Sheets, Popovers, Tab bars, Keyboards, The menu bar), SwiftUI API docs, WWDC24 10147 and WWDC25 208/256. Citations inline per finding.
  • Applied the prototype on branch prototype/ipad-ui-audit, rebuilt, and re-ran the same scripted walk for like-for-like after shots.

3 · Findings

Critical

F1 — Every command surface is full-bleed on a 13″ canvas

The input bar, result list, shelf, and paste chip are all maxWidth: .infinity with fixed 12–16 pt padding. On the 13″ iPad a ranked result row spans the entire window: label at the far left, action glyph at the far right, ~85% of the row empty. Apple's readable-content guide tops out around ~660–700 pt for exactly this reason; the HIG's iPad framing is "elevate the content people care about" — not "fill the display".

Code: ResultListView.swift:88, RootView.swift:722–827 (bottom bar), InputBar.swift · Fix prototyped (§4) · HIG Layout, Designing for iPadOS

High

F2 — Favorites grid is hard-coded 2×2; one favorite becomes a half-screen slab

HomeView.swift:84 pins the grid to two flexible columns. With one pinned favorite, the card is half the window wide (~1,000 pt in portrait); Recents rows below it span the full width. The grid should be column-count-adaptive inside the readable column (4-across at regular width) — LazyVGrid with adaptive/size-class columns is the standard mechanism.

Code: HomeView.swift:24, 84–108 · Fix prototyped · LazyVGrid

High

F3 — Capture breadcrumb crumbs stretch into enormous cards

The breadcrumb gives each crumb an equal weighted share of the measured container — the full window. On 13″ each of TITLE / DUE DATE / LIST becomes a ~450 pt card for a one-word value. The capture input at the bottom is likewise full-width.

Code: Capture.swift:800–822 (bar), crumb weighting ≈ Capture.swift:1042–1058 · Fix prototyped

High

F4 — No hardware-keyboard support beyond Return

Zero .keyboardShortcut, no onKeyPress, no arrow-key result navigation, no esc. A launcher is the keyboard-first app category, and iPads routinely have Magic Keyboards; the HIG says people "generally expect to rely on the standard keyboard shortcuts that work in other apps". Expected baseline:

KeyAction
⌘K (or any typing)focus the search field
↑ / ↓move the highlight through results (needs Core: highlight is currently pinned to rank 0)
⏎run highlighted ✓ already works
escclear query → exit capture / Search Files context
⌘1…4run Favorites 1–4
⌘,open Settings

On iPadOS 26 the same .commands { } API that builds macOS menus now populates the iPad menu bar — the shortcut table above should land there so it's discoverable (hold ⌘ shows the HUD for free).

HIG Keyboards, The menu bar · keyboardShortcut · WWDC25 256

High

F5 — Keyboard-lift math assumes the window is the screen

RootView.swift:851 computes keyboard overlap as UIScreen.main.bounds.height − endFrame.minY. UIScreen.main is deprecated, and in Split View / Slide Over / Stage Manager / iPadOS 26 windowing the window is not the screen — the bar gets lifted by the wrong amount. A floating or split iPad keyboard feeds the same math a small detached frame, and the 120 pt software-keyboard threshold in KeyboardBarLift.swift:19 sits in ambiguous territory for Magic Keyboard accessory bars. SwiftUI's own avoidance is disabled globally, so nothing falls back to system behavior when this math is wrong.

Fix: convert the keyboard frame into the app window's coordinate space (or adopt keyboardLayoutGuide with followsUndockedKeyboard), treat floating/split keyboards as zero overlap, and keep the policy in Core where it's already swift test-gated.

Code: RootView.swift:851, Core/…/KeyboardBarLift.swift:19, KeyboardFrameObserver.swift · keyboardLayoutGuide / followsUndockedKeyboard

Medium

F6 — Management pages: full-width forms, toggles a metre from their labels

Settings hub, provider pages, Custom Actions, Fallbacks, Snippets, Shortcuts, File Search, Pile — all rows run edge-to-edge with a switch or chevron on the far right. The prototype deliberately left these untouched (scope: launcher surfaces), but the same readable-width treatment applies — either the command-column clamp or grouped-list styling that respects the readable guide.

Code: SettingsView.swift, ProviderPages.swift, per-page views · HIG Lists and tables

Medium

F7 — No pointer (trackpad/mouse) affordances

No .hoverEffect anywhere: result rows, favorite cards, shelf buttons, and crumbs give zero hover feedback with a trackpad. iPadOS 26 pointer behavior makes the hover highlight the primary "this is clickable" signal. The prototype adds .hoverEffect(.highlight) to result rows and favorite cards; shelf buttons, recents, crumbs, and the paste chip should follow.

Code: ResultListView.swift, HomeView.swift, FallbackShelfRow.swift · HIG Pointing devices, WWDC25 208

Medium

F8 — No window configuration for iPadOS 26 resizable windows

The scene is a bare WindowGroup: no minimum content size, no default size. On iPadOS 26 windows resize arbitrarily (and UIRequiresFullScreen is deprecated-and-ignored) — the app should declare .frame(minWidth:minHeight:) + .windowResizability(.contentMinSize) and be QA'd at half/third/quadrant tiles. The command-column clamp makes resizing non-destructive by construction (layout reverts as the window grows back — a WWDC25 208 requirement).

Code: QuickieApp.swift:97–110 · HIG Multitasking · windowResizability

Medium

F9 — Share sheet is an unanchored full sheet

The Share secondary action wraps UIActivityViewController in a plain SwiftUI sheet. The iPad-native pattern for a transient action on a specific row is a popover anchored to that row (HIG: reserve popovers for wide views — this is exactly that case). Same for future transient pickers.

Code: RootView.swift:2174, 1260 · HIG Popovers · presentationCompactAdaptation

Low

F10 — Shelf peek sizing degenerates on wide windows

The shelf solves for a button diameter so that k buttons + a half-button peek exactly fill the row. On a 1,376 pt row it always resolves to the 52 pt maximum, never scrolls, and the "there's more" peek cue disappears while buttons hug the leading edge. The command column fixes this for free — the measured row is ≤ 680 pt again, back inside the rule's design envelope.

Code: Core/Sources/QuickieCore/FallbackShelf.swift:113–130, FallbackShelfRow.swift:73

Low

F11 — Editor sheets are already decent; make the sizing explicit

Good news: the Custom Action and Snippet editors already present as centered cards on iPad (see gallery). Adopt .presentationSizing(.form) (iOS 18+) so the intent is explicit rather than an accident of defaults, and audit any custom sheet backgrounds against Liquid Glass insets.

Code: RootView.swift:1221–1247, CustomActionsView.swift:104, SnippetManagerView.swift:85 · HIG Sheets · presentationSizing

Low

F12 — Landscape empty states drift off-balance

With the keyboard docked in landscape, only ~3.5 rows fit above the fold and the brand-mark placeholder sits visually off-center between breadcrumb chrome and keyboard. Minor today; worth re-checking after the column ships, and worth a deliberate empty-state composition for short-and-wide windows (Stage Manager half-height).

Evidence: img/before-01-home-landscape.png, gallery §7

4 · Prototype: the readable command column

Branch prototype/ipad-ui-audit (built, walked, screenshotted on the same simulator). One new modifier, applied at six sites — launcher bottom bar, result list, file-search list, Home recents, Favorites band, and both breadcrumb bars — plus size-class-adaptive Favorites columns and hover effects:

struct CommandColumn: ViewModifier {
    @Environment(\.horizontalSizeClass) private var hSize

    func body(content: Content) -> some View {
        content
            .frame(maxWidth: hSize == .regular ? 680 : .infinity)
            .frame(maxWidth: .infinity)   // centers the clamped column
    }
}

Size class — not UIDevice.idiom — is the switch, so an iPad app windowed to half-width (compact) keeps today's iPhone layout, exactly as the HIG prescribes. Full-bleed layers (mesh backdrop, progressive-blur bands) intentionally stay edge-to-edge; only content clamps. All existing iPhone snapshots are unaffected (compact width is a no-op).

5 · Direction alternatives

A · Centered command column — prototyped, recommended first step

What §4 shows. Keeps the product's bottom-anchored, keyboard-adjacent interaction model fully intact — results still stack up from the input, best match nearest the thumb/cursor. Lowest risk, no navigation rework, immediately makes 100% of screens feel intentional on iPad.

B · Spotlight-style floating palette (concept mock)

With a hardware keyboard there is no on-screen keyboard — the bottom-anchored bar floats alone at the foot of a big empty canvas. The natural iPad-with-keyboard shape is the Spotlight/Raycast palette: input near the top, results dropping downward, eye-line at the top third. This inverts the "rank 0 nearest the input" stack (rank 0 would sit directly under the field — still adjacent) and earns its keep only when a hardware keyboard is attached (soft-keyboard mode should keep layout A).

C · Two-pane management (concept mock)

The launcher's management pages are a textbook sidebar/detail shape: path: [ManagementPage] on one stack would map directly onto NavigationSplitView at regular width — launcher stays live on the left, Settings/provider pages open on the right instead of covering the launcher. Typing a provider name still deep-links, but the launcher never disappears.
